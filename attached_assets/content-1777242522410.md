The URL Fragment

A URL has two parts. Everything before the `#` is sent to the server as an HTTP request. Everything after the `#` (the fragment) is not sent to the server. The HTTP specification prohibits browsers from including the fragment in the request. It stays in the browser. The server never receives it.

This is the foundation of everything Nowhere does. All content is encoded into the URL fragment. When you open a Nowhere URL, your browser requests the same static shell page from `nowhr.xyz` for every visitor. The server delivers that file. Your browser then reads the fragment, decodes it locally, and renders the store, forum, or petition entirely from what was already in your address bar before the request was made.

The server sees only that someone requested a page. It does not know which store or forum. It has no way to know. The fragment, from the server's perspective, is invisible.

Encoding Everything

A store or forum can carry a substantial amount of data. That data has to fit in a URL short enough to share and copy reliably. Nowhere compresses it through a five-step pipeline.

**Serialize.** The data structure is converted to a compact text representation. Fields are separated by delimiters. Optional fields are omitted entirely. Booleans are packed into a base64url bitfield. The goal is to represent everything while losing nothing, as concisely as possible before any compression runs.

**Substitute.** A dictionary of common words, phrases, URL prefixes, and emojis is applied. Frequently used words are replaced with one or two character codes. Hundreds of substitutions run before the compression algorithm sees the text, reducing character count significantly for English text.

**LZ77.**`deflateRaw` from the pako library first applies LZ77, the first stage of raw DEFLATE. LZ77 scans the data for repeated byte sequences and replaces them with back-references: a length and a distance pointing earlier in the stream.

**Huffman.** The LZ77 output is then Huffman coded. Each symbol is assigned a variable-length bit code based on how frequently it appears: common symbols get shorter codes, rare symbols get longer ones. Together, LZ77 and Huffman coding form raw DEFLATE, the same compression inside gzip and zip, without wrapper headers.

**Encode.** The compressed binary is converted to base64url. The result is URL-safe characters that require no percent-encoding in a fragment.

Decoding is the same pipeline in reverse: `base64urlToBytes` → `inflateRaw` → `restore` → `deserialize`. Both directions run entirely in the browser.

URL Encryption

Any Nowhere site can be encrypted before the URL is finalised. When a creator chooses this option, the encoded fragment (the output of the five-step pipeline) is passed through an additional encryption layer. The result replaces the normal fragment in the URL.

To the renderer, an encrypted fragment appears the same as a malformed or corrupted one. Both fail `inflateRaw` and produce the same decode error. The error page presents a password input with a note that the URL may be encrypted. A technical observer who knows the protocol can infer encryption from a fragment that fails DEFLATE decoding but is of an appropriate length; the renderer intentionally does not signal this distinction itself.

Verification Phrases

The **owner phrase** is derived from the creator's public key. It is the same across every site, forum, or post that keypair publishes. Sharing an owner phrase is how a creator proves consistent identity across unrelated URLs, without accounts or usernames. It is the primary way to know that two sites were made by the same person.

The **site phrase** fingerprints the URL content. Two URLs with the same phrase are content-identical; any change to the URL produces a different phrase. It can be read aloud or compared between devices to confirm a link has not been altered.

Signed URLs bind both together. The creator embeds a signature in the fragment, covering the exact content. Any browser can verify it using the public key already encoded in the URL, with no external service. A signed URL proves the holder of that private key published this exact content, and the owner phrase identifies who that keypair belongs to across all their work.

The pure Nowhere sites

Five of the eight Nowhere tools are entirely static. The message, the event, drop, art, and the fundraiser require nothing beyond the codec. No relays. No keys. No dynamic state. Each is fully defined by its URL fragment and renders without any network request beyond loading the decoder.

Nostr Relays

Static content lives in the URL. But some Nowhere features require live communication: orders arriving at a seller, signatures accumulating on a petition, posts appearing in a forum. For that, Nowhere uses Nostr relays.

A relay is a server that stores and forwards signed Nostr events. An event is a JSON object. The relay stores it, forwards it to subscribers who request it by filter.

Every event Nowhere sends to a relay has its content encrypted before it leaves the browser with NIP-44. The relay receives an opaque blob that it cannot read.

Nowhere uses kind 30078 (NIP-78 parameterised replaceable events) for persistent data (orders, petition signatures, forum posts) and kind 21423 (ephemeral events) for transient communication. Ephemeral events are not stored by relays that follow the Nostr specification. They are forwarded to currently connected subscribers, then discarded.

You can configure which relays your forum or store uses. You can even run your own.

The Store

A store URL encodes everything: the seller's public key, the product catalogue, descriptions, pricing, shipping rules, payment address, return policy. The buyer's browser decodes the entire store from the fragment. No server is consulted. No account is needed to browse. No internet connection is needed to create a store or to load the contents of a store from a URL.

When a buyer places an order, the browser generates a fresh keypair. This keypair is created for that single order and never used again. The order contents (items, quantities, and delivery address) are serialized, then NIP-44 encrypted so that only the seller can decrypt it. The encrypted event is published to the relay as kind 30078. The throwaway key is then abandoned.

The relay stores an encrypted event from a public key used exactly once with no information identifying what store it was for, what the order was or who placed it.

Inventory state uses a separately derived keypair: `HMAC-SHA256` with key `"nowhere-inventory"` and the URL fragment as the message. The first 15 hex characters of `SHA-256(fragment)` form a lookup hash that identifies the store's inventory events on the relay without revealing the store's identity or content to the relay.

The Petition

A petition's statement is entirely in the URL fragment. The creator's public key is embedded in the codec. Any browser that opens the URL can decode and display the full statement without consulting any server. The statement cannot be altered after the URL is published, since changing any character produces a different fragment and a different petition.

Signatures are NIP-44 encrypted and then published to a Nostr relay as a kind 30078 event with a `d` tag in the form `nowhr/<hash>`, where the hash is the first 16 hex characters of `SHA-256(fragment)`. This identifies which petition the signature belongs to. It does not reveal the petition's content or the creator's identity to anyone who doesn't already have the URL.

The Forum

A Nowhere forum is a persistent community whose encryption keys are derived entirely from the URL fragment. Everyone who has the URL has access. No one who lacks it can read anything the forum contains.

The forum has never been registered anywhere. No relay knows it was created. No server holds the keys. Posts, replies, and live chat all use Nostr relays as transport infrastructure, but the relays cannot identify which events belong to which forum without the URL fragment. An outside observer cannot tell which replies belong to which forum or any details about who or how many users a forum has.

The sections below describe the architecture from the cryptographic foundation up.

Forum - Key Derivation

Everything in the forum traces back to one operation. `HMAC-SHA256` with the key `"nowhere-forum"` and the URL fragment as the message produces a 32-byte output used directly as a private key. The corresponding public key is derived from it via standard elliptic curve multiplication. This is the forum's cryptographic identity. Anyone with the URL fragment can compute it. No one else can.

Topics each get a unique filter tag: `SHA-256("nowhere-forum-topic" + forumPrivKey + topicName)`, truncated to 32 hex characters. The general chat channel gets its own: `SHA-256("nowhere-forum-chat" + forumPrivKey)`. Each post gets a tag derived from its content: `SHA-256(postText + authorPubkey + String(timestamp))`. Reply threads derive a keypair from the same post data using `HMAC-SHA256` with key `"nowhere-reply"`.

Private chat rooms derive a keypair from `HMAC-SHA256` with key `"nowhere-chat-room"` and message `forumPrivKey + roomName + \0 + accessCode`. The null byte separates the room name from the access code. Different access codes produce entirely different keypairs. The room is meaningless without knowing the access code.

None of these keys are stored permanently anywhere. They are recomputed from the URL fragment on each page load. There is no key server. There is no key backup. The URL fragment is the key material. Losing the URL means losing access.

Forum - Posts and Encryption

When a user writes a post, the browser constructs a payload containing the title, body, the author's public key, and a Unix timestamp. Before the payload is encrypted, it receives an inner signature.

The inner signing uses `finalizeEvent` from nostr-tools to construct a kind 21423 Nostr event. The content of this inner event is the post's JSON wrapped by `wrapContentForSigning`: the content is first NIP-44 encrypted using a constant conversation key shared among all forums, then prefixed with the literal string `"Signed for nowhere - nowhr.xyz"`. The Schnorr signature from this inner event is extracted and embedded in the post payload as the `sig` field. Anyone who can decrypt the outer post can then verify the inner signature, confirming the author held the private key at the time of writing, without that key appearing anywhere in the outer event.

The completed payload is encrypted for the outer event. A fresh keypair is generated to publish the event.

The outer event is a Nostr kind 30078. The encrypted blob is the content. The throwaway key is the event author. A single `t` tag contains the topic's derived hash: 32 hex characters that are meaningless without the forum private key. Forum reply timestamps are shifted backward by a random 0 to 4 days. This prevents any observer from correlating post timing metadata.

Forum - What the Relay Sees

The relay stores kind 30078 events. Each has a different throwaway public key per post, an encrypted content blob, a timestamp somewhere in the past four days, and a `t` tag: a 32-character hex string derived from the topic hash and the forum's private key.

The relay cannot read the post content. It cannot identify the real author of any post. It cannot count how many members the forum has, or determine what the forum is about. Under pressure, a relay operator can delete events by their cryptographic ID. But the relay has no mechanism to search for forum posts by community, by topic, or by content.

Forum - The Salt

When a forum is created with the salt option enabled, the URL takes the form `https://nowhr.xyz/s#<fragment>*<base64url-salt>`. The `*` separates the encoded forum codec from the salt. Both parts are in the URL fragment. Neither is sent to any server.

A different salt produces a different private key, a different public key, different topic tags, different everything. A forum with a different salt is cryptographically unrelated to the same forum without that salt, even on the same relay.

The practical consequence: if a relay begins filtering its events the forum members can enter a new salt and appear as a totally different forum to the outside world. The forum continues under a new cryptographic identity that the relay cannot link to the previous one.

Forum - Live Chat

Forum chat uses ephemeral Nostr kind 21423 events. A relay conforming to the Nostr specification does not store ephemeral events. It forwards them to currently connected subscribers and discards them. Chat messages are not archived on the relay. There is no message log to hand over.

Three chat channels exist. The general channel encrypts to the forum keypair, so anyone with the URL can read it. Private rooms encrypt to a keypair derived from the room name and access code; only members who know both can decrypt. Private messages between two members encrypt to the recipient's session keypair. Each message in every channel is sent from a fresh throwaway key generated for that message alone.

Each chat message carries the same inner signing structure as a forum post: the message content is signed with the author's session key inside the encrypted payload. A recipient who decrypts the message can verify the signature. The relay cannot, because it cannot read the payload.

Forum - Web of Trust

A forum can optionally apply a Web of Trust filter. The creator configures three separate depth levels: one for posts, one for replies, one for chat. Depth 0 means no filter: all decryptable content is shown. Depth 1 shows content only from Nostr pubkeys that the viewer directly follows. Depth 2 includes follows-of-follows.

The filter operates at the display layer, not the relay layer. The relay delivers all encrypted forum events matching the topic tags. The browser decrypts each, extracts the author's public key from the inner payload, and checks whether it falls within the trusted set. Events from untrusted pubkeys are silently dropped before display. The relay never learns which events were shown and which were filtered. The trust computation is invisible to the network.

Open Source and Self-Hosting

The Nowhere renderer is a static HTML and JavaScript application. The source code is open.

Anyone can clone the repository and deploy their own instance on a personal server, a shared host, or a local machine. Running it locally requires nothing more than a static file server: `python3 -m http.server` in the build directory, then open a browser at `localhost:8000`. A Nowhere URL created on `hostednowhere.com` or `nowhr.xyz` decodes identically on any other instance. The codec is an open protocol. Two decoders that implement it correctly produce identical output for the same URL.

If one domain becomes unavailable, any deployed instance of the decoder, including a local one, renders any existing Nowhere URL identically.
